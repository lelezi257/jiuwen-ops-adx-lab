01 · DECISIONS

先把这一版的选择说清楚

运维控制器判断“是哪件事”，ADX 解决“在哪里运行”，Swarm / Core 执行“怎样处理”。

本页只有设计，没有切换现有系统。

现有工作台、真实模型、PR/CI/发布链和历史数据继续按原实现运行。本页示例中的 case、Binding、Session 和接口回执均为设计示意，不是新验收证据。标记：已有事实 本项目拟新增 需环境验收。

① 一个事件一个承载身份

同一事件的补充证据、修复和复核复用同一 Binding。不同事件按需创建独立沙箱，不预先启动一批运维 Agent。

② 保留真实九问执行链

沙箱里运行我们的薄执行服务，由它调用官方 Process SDK；SDK 启动 Swarm / Core 子进程。HTTP 封装不替代 Agent loop。

③ 先做能解释、能回看的闭环

首版事件未结束时不自动暂停。结案后确认回执和轨迹可读，再释放沙箱；自动休眠和进程 Checkpoint 另行验证。

当前事实 现有 runner 常驻轮询，但官方 SDK 的执行子进程本来就是按次创建。ADX 带来的变化是进一步让整个执行环境按需分配，并提供跨环境的稳定访问、资源与生命周期管理。见 R1、J1。

接入选择 优先使用 ADX 的 Agent Template + AgentBinding + 受管 HTTP 转发，不在 Ops Lab 再实现一套裸 Environment 的创建、缓存 IP 和路由管理。初版固定数字模板版本，暂不引入 Alias 灰度升级。

02 · DEPLOYMENT

仍是一台 VM，公共服务常驻，Agent 沙箱按需

图中的框表示部署边界；Swarm、Core 是沙箱内官方子进程中的模块，不是额外的 HTTP 服务。

部署组进程 / 容器关系生命周期与角色
现有运维公共服务control、evidence、delivery、probe 与观测栈保持独立服务；调度模块先放 control 内。常驻，保留真实 PR/CI/构建/发布、业务验证和数据库。
ADX 单机底座Redis、Coordinator、adxlet（内嵌 Relay）、adx-apiserver（内嵌 Ingress，启用嵌入式 Activator）、独立 sandboxd。常驻；不部署每个事件的空 Agent。嵌入式 Activator 仍有独立职责，后续可拆进程。
事件执行沙箱每个活动事件一个 Environment；Execd 启动镜像中的运维执行服务；SDK 按执行启动官方子进程。第一次需要 Agent 时创建。镜像构建、模板发布均不等于沙箱已启动。
原生观测一个原版前端；传输适配器按 recording root 选择隔离的只读读取上下文，必要时以 helper 进程隔离全局路径。常驻入口；只读 helper 是观测进程，不是运维 Agent。历史可在执行资源释放后继续读取。
部署前置条件待核实，不把容器名字当能力证明。

沿用现有 Linux VM、Docker Compose 应用栈；新增 ADX 安装目录、Redis namespace、sandboxd 网络和证书，不重建 VM。已有 VM 为 4 vCPU / 10 GiB，新增底座后的资源余量必须先测量。首选 runc 后端；包的 ARM64 支持、sandboxd / Execd 版本、路由到 Compose 工具服务和真实模型服务均需验证。不以 Mac 宿主、Docker ready 或 TCP 端口可连接替代 Agent 就绪。

03 · IDENTITY

一个“Session”不能同时代表工单、对话和容器

本方案不另造一个叫 session_id 的业务字段：用 case_id 表示运维事件，用 sdk_session_id 表示九问真实会话。

身份谁创建 / 保存复用与变化规则
case_id运维控制器；现有事件对象。同一故障的告警归并到同一 case。当前按故障 release 去重的规则可先保留，扩展时增加租户 / 服务 / 环境范围。
binding_id + template version控制器选稳定地址；ADX 管理 Binding。完整作用域还包含认证租户及模板。事件活动期间复用；不将 SDK SessionID 当 BindingID，也不每次调用 template URN 生成随机新 Binding。
environment_id / RuntimeADX 当前 Binding 引用 Environment；Platform 管运行身份与生命周期。首版固定模板，复用 current Environment。Runtime 可因恢复 / 重启变化；不是 Swarm Session。不能从 BindingID 猜真实 EnvID。
attempt_id / execution_id控制器原子预留一次业务执行；execution_id 直接使用 attempt_id。网络重发不增加 attempt；明确业务重试才创建新 attempt。接收回执、模型执行状态和结果提交分别记录。
sdk_session_id从官方 run 事件与回执登记；保留 request_id。repair 与 verify 默认不同真实 Session；一个 attempt 内不换 Session。补充同一对话必须显式指定已有 ID，并保留它的持久状态。
recording_root控制器分配受限事件目录并登记 Session 索引。首版每个事件一个独立数据根；后继运行承载复用前须确认旧写者退出。模型和客户端不能提交任意主机路径。
“找不到 Session”要分两种。

没有业务事件：先归并或创建 case；没有 SDK Session：让官方执行创建并回报。只有不存在合适的执行承载时才需要激活 Environment。存在 Session 历史并不代表沙箱还活着；沙箱活着也不代表已经有这次执行的 Session。

04 · END-TO-END FLOW

从第一次订单 500，到释放执行资源

点击阶段查看“谁对谁做了什么”。下面是设计讲解器，不会调用模型、启动沙箱或操作真实案例。

1．实际 500 告警先归到一个事件

控制器识别服务、环境与故障 release；重复告警追加到已有事件，不重复申请 Agent。

交互
订单请求 → 监控 → control.create_case()
保留证据
真实告警、业务检测、故障 release / source；此时还没有 SDK Session。
页面解释
业务异常；事件等待分配执行资源。不是“Agent 已开始调查”。
阶段交互顺序控制器必须知道的结果
1 告警Alertmanager → control：归并 / 新建 case。是否新事件；故障属于哪个真实 release。
2 预留执行control 的调度模块：按 case 原子登记 Binding 选择与 attempt，写入待投递执行。资源尚未就绪不进入 REPAIRING；同 case 仅一个活动执行。
3 激活control → ADX Gateway；Activator 读取模板 / Binding，首次访问创建稳定身份；Platform → adxlet → sandboxd → Execd 启动镜像服务；Gateway 等可用路由后转发。真实 Binding / Environment 身份、启动失败或结果未知；业务服务 /ready 完成 SDK 能力检查。
4 修复执行服务持久化接受 attempt → 官方 SDK → Swarm / Core → 模型；host tool 回调 → evidence / delivery；事件与真实 SessionID 回报 control。SDK 实际开始后才标记 REPAIRING；工具证据、候选 SHA、PR 与官方回执互相对应。
5 交付control / delivery ↔ GitHub CI → 门控合并 → 精确源码构建 → digest 发布。修复 SDK 已结束，页面显示等待 CI / 构建 / 发布；不新增假的 Core Span。
6 恢复复核probe 对真实 HTTP / 金额 / 数据库独立验证；control 经相同 Binding 再送 verify attempt；SDK 新建真实只读 Session。同事件 / 同活动承载 / 新 Session。真实恢复验证通过与 SDK 复核通过共同决定 RESOLVED_FIXED。
7 结案清理控制器确认结果和记录已落盘、SDK 子进程结束、Observer 可读取 → 写入清理意图 → 经 ADX 删除该活动 Binding。删除确认后标记执行资源已释放。业务 case / Session 索引 / 目录和原始证据继续保留；删除未知不能宣布释放。
8 后续输入活动 case 补充请求继续走原 Binding；结案 case 的显式重开创建新承载轮次 e2。重开不篡改 e1 身份；是否继续已有 SDK 对话由业务显式选择。旧执行退出未确认前，禁止新旧写者共用数据根。
05 · INTEGRATION

ADX 接 HTTP；Process SDK 仍在沙箱本地接官方进程

控制器不需要成为 Process SDK 客户端，也不把 SDK 的 stdin/stdout 直接暴露成公网协议。

ADX 已有

不可变 Template、受管 Binding 激活、HTTP/SSE / WS 透明转发、Environment 调度与生命周期、参数化目录挂载；公开目录 / 管理查询不等于业务健康。

九问已有

Client.run() 创建官方命令进程、JSONL 双向协议、host tool 回调、取消、结构化结果；传 session_id 可请求复用已有会话的持久状态。

Ops Lab 新增

按事件调度、沙箱执行 HTTP API、一次执行的持久接收 / 去重 / 回查、受限授权、跨沙箱 Session / 记录索引。ADX 不替我们理解故障或保证 PR 只创建一次。

模板发布与第一次请求

先构建包含当前官方依赖锁和执行服务的镜像，再发布 ADX 模板。发布请求不填 version，使用服务端返回的数字版本；将镜像 digest、模板版本和九问锁定提交登记到 Ops Lab 配置。模板声明 HTTP 8080、资源、目录挂载与就绪检查；镜像自己的 ENTRYPOINT/CMD 启动执行服务，Execd 由 ADX 平台注入。

运维控制器发出（设计示例）
POST https://ADX_GATEWAY/agent/http/runs
  ?target=urn:adx:binding:ops-order:1:ops-case-123-e1

{ "case_id": "case-123", "attempt_id": "attempt-r1", "phase": "repair" }

ADX 负责：选 Binding → 按需激活 → 路由转发
我们负责：/runs 的业务语义、执行授权、接收落盘、SDK 调用和回执

沙箱内：执行服务 → Client.run(...) → 官方 CLI → Swarm Runtime → Core
工具链：SDK on_tool_call → 受限工具入口 → evidence / delivery
这是两层不同的接口。

/agent/http 和 Binding URN 是 ADX 官方入口；/runs、/ready、状态回查和取消是本项目拟新增的执行服务接口。ADX 移除平台凭据后转发业务请求，业务执行授权需要另外设计，不能依赖原始 ADX API Key 被透传到沙箱。

模型与工具凭据的传递

ADX 租户 Key 只留在控制器 / 调度侧；GitHub Key、Docker socket 和平台管理凭据留在可信服务。沙箱使用短期、绑定 case / attempt / phase 的执行凭据，工具代理在服务端重新绑定 case 并核验允许操作，再以原有服务身份调用 evidence / delivery；verify 的只读限制要在代理侧执行，不只写在 Prompt 里。

模型调用仍是真的。单机初版可由部署侧将受保护的模型配置文件只读挂载进执行环境；执行服务启动时加载，不写入镜像、Template、公开回执或普通 X-ADX-Parameters。这是本项目需要实现的配置加载与权限准备，不是 ADX 已有专用 Secret 服务。后续再替换为短期模型代理凭据。

06 · LIFECYCLE

按需创建先落地，自动休眠另设门槛

第一次收到事件时创建，事件结束后释放，已经能避免大量空 Agent 常驻。首版不把运行到一半的模型任务当成可随时安全暂停。

情况本方案处理方式边界
首次启动 / 资源不足显式记录等待资源、启动中与未就绪；在原 deadline 内查询同一 Binding，不换 ID 规避失败。ADX 控制创建和调度；控制器解释业务进度。TCP 可连接仍需业务 /ready 检查 SDK 能力。
HTTP 返回丢失同一 attempt 原身份回查；只有确认未接受才可再次投递。沙箱 /runs 用 execution_id 去重。ADX 环境创建幂等不等于模型执行、工具副作用、PR 创建幂等；写入结果未知不盲目重放。
执行服务 / SDK 崩溃现有 lease 失效后进入需核查状态；先查回执、PR、运行版本和任务日志，显式决定新 attempt。保留现有“不自动重放有副作用任务”的原则。平台恢复进程不等于业务从最后一个工具调用精确继续。
CI / 构建等待首版保留同事件沙箱，不运行模型；等待结束后送入新的 verify attempt。这是事件处理期间有界保留资源，不是为所有潜在事件预建 Agent。并发额度和最长等待需要可配置。
自动暂停（后续）ADX 已有 idle_action=pause 和访问触发 EnsureRunning；选定后端并实测 Checkpoint、活动检测和模型连接后再开启。后台任务不必然阻止 idle；202 后的后台 SDK 可能被错误视为空闲。初版模板 idle timeout 为 0，禁止靠网页长连接冒充执行保活。
取消 / 终止控制器撤销本 attempt 的工具权限，通知 SDK cancel，等待子进程结束与回执刷新，再申请 ADX 清理。浏览器断开或关闭 SSE 不代表任务取消。已有 PR、已提交发布不因取消而消失。
结案释放保存清理意图、核对 Observer 已可读、确认停止写入，再删除活动 Binding；后台对账只重试清理，不重试修复。保留 case 的历史 Binding/Env 快照和全部记录。ADX Binding 删除与业务 case 删除是不同动作。

并发分两层：同 case 只能有一个活动 SDK 执行；不同 case 可有独立承载，但必须受 VM 配额限制。针对同一服务 / 环境的合并与发布仍串行、核验 expected release，不能因沙箱独立就允许两个修复互相覆盖。初始并发额度可设为 1，环境资格通过后再增加；设计验收用两个只读取证事件验证独立承载，不同时破坏同一个订单应用。

07 · DATA & OBSERVATION

沙箱可以消失，事件和原生轨迹不能消失

现在的单 runner 共享卷要改成多事件记录目录和可信索引，原版 WebUI 继续显示真实 Session 的原始轨迹。

宿主机持久目录（示意，路径由控制器生成）
/var/lib/ops-lab/cases/<case_id>/
  swarm/                  # 官方 Session 状态与 .trace 数据；由对应沙箱单写
  reports/<attempt_id>/   # 官方结果回执、投递日志；不保存敏感请求头

沙箱：/data → 仅本 case 的目录，可写
Observer：/recordings → 经授权的事件目录，只读
control：case / Binding历史 / attempt / Session / recording_root 索引
delivery：仍有自己的源码工作区，和上述 SDK 状态不是同一目录
数据持有与访问规则不能推导出的结论
业务事件和发布事实control / delivery 原有持久卷保留；ADX Redis 单独保存平台状态。ADX Redis 正常不代表业务恢复；Agent 完成不代表发布通过。
SDK 状态与原生 Trace同 case 独立根目录；Observer 读取官方 Session 元数据和官方 Trace 存储。保留 SQLite WAL 所需文件访问条件，禁止直接复制正在写入的单个 DB 文件当完整归档。文件存在不代表任意中断都能继续执行。轨迹需要实际可读水位 / 终态归档验证。
多根目录读取Session 索引定位 recording_root；读取上下文隔离。若官方查询依赖全局数据目录，就为每个活动根使用受限只读 helper 进程。不能为每个请求改全局环境变量或切换共用软链，否则并发读取会串 Session。helper 细节需实现阶段验证。
原生前端继续使用锁定版本原版 UI；自有事件跟随栏显示 case / Binding / Environment / attempt / 真实 Session。不把两个 SDK Session 合成一个，不把创建沙箱、CI、发布事件插入 Core Span。
AFS / 多节点后续可把同一目录契约接到 AFS 或其他共享存储；验证 POSIX / SQLite WAL、写者排他、跨节点访问和故障恢复。ADX 支持挂载不等于已集成 AFS；本地目录的验证不能代替跨节点恢复验收。

读取历史不应唤醒 Agent。观测服务通过记录索引读持久文件，不经受管 Harness 业务入口。结案清理前必须确认真实 SDK 回执已落盘、轨迹水位可读和进程已退出；保留期由实验配置控制，不继承现有 7 天参数就宣称永久留存。

08 · PROPOSED CONTRACTS

最小接口只包执行，不再包一层模型循环

以下均为拟新增产品合同。已有 SDK / ADX 接口与我们自己的 HTTP API 分别标注。

接口 / 数据责任与语义成功表示什么
ADX /agent/http + Binding URN
官方已有		验证平台身份，选 Binding，按需激活并透明转发；固定实际版本与镜像来源。选到身份或返回 ID 不表示模型已执行；需分别检查服务和任务状态。
GET /ready
执行服务新增		不调用模型；验证配置加载、SDK capabilities、持久目录可用。部署探针与控制器共同使用。执行宿主可接受任务；不代表订单业务正常。
POST /runs
执行服务新增		校验受限授权和 phase；以 attempt_id 持久保存接收状态与规范化请求摘要，同 ID 相同请求返回既有状态，不同请求拒绝。202 只表示已可靠接受；收到官方 SDK 的实际开始事件后才记录执行开始，不预设或伪造模型调用。
GET /runs/{attempt_id}
执行服务新增		回查 accepted / running / completed / failed / outcome_unknown，返回真实 Session 与官方回执摘要。断连时对账使用；客户端不得据超时新建另一个 attempt。
POST /runs/{attempt_id}/cancel
执行服务新增		持久化取消意图，传给 SDK cancel；不能仅终止 HTTP 连接。收到取消不表示子进程退出；退出确认和清理另有状态。
受限执行 / 工具入口
control 内的 broker 模块		接收沙箱事件、心跳、结果、工具请求；校验凭据的 case / attempt / phase / 到期时间；服务端重新绑定 case 并裁剪权限。不是把当前全局 runner_token 发给每个沙箱。原 delivery 门控和独立业务验证继续保留。

11 · IMPLEMENTATION GATES

实施时分段验收，先证明承载，再接完整修复

本页没有执行以下阶段。每阶段留下独立证据，不能用组件能力或已有 Docker 案例代替 ADX 产品 E2E。

阶段实际要验证的行为退出证据
A 环境资格不打断现有任务，安装固定版本 ADX / sandboxd；验证 ARM64、runc、磁盘 / 内存、内部工具路由、模型出口、受保护配置与挂载。版本 / 配置清单、真实 Environment、业务 /ready 与 SDK capabilities；资源测量。无模型替身。
B 最小真实执行没有 Agent 沙箱 → 一个只读取证事件 → 一次受管请求按需启动 → 真实 SDK / 模型 / 工具 → 回执、Session 与原生轨迹可对应。case / Binding / Environment / attempt / SDK Session 身份链；真实工具证据；未预创建实例的目录查询记录。
C 身份与故障边界同事件重复请求不产生第二次执行；两个不同只读事件分别承载；模拟 HTTP 回执丢失后回查同 attempt；取消后不接受越权工具调用。环境与 SDK 执行计数、去重记录、受限授权拒绝、迟到回执和 outcome_unknown 的处理。
D 完整订单案例快速正常基线 → 实际 500 → ADX 沙箱修复 → 真实 PR/CI/构建/digest 发布 → 原独立恢复合同 → 同 Binding 的新 verify Session → RESOLVED_FIXED。真实业务三段证据、PR/CI与发布身份、repair / verify 原生轨迹；打开一次观测页连续跟随，不伪造 Core Span。
E 释放后可回看终态回执 / 轨迹刷新完毕后删除活动 Binding；原生页仍可读两个 Session；重开事件采用新承载轮次并保持旧记录。ADX 删除确认、持久目录与只读回看、无旧写者并存，case 与历史身份未丢失。
后续独立阶段自动暂停 / Checkpoint 恢复、AFS / 多节点、增加并发额度与别名升级。分别建立后端、存储与业务执行的真实验收，不混入单机首版通过结论。

实施切换原则：先在同 VM 的独立目录和端口准备底座，现有 runner 保持原样；最小链路通过后，空闲时显式切换执行后端，不能让旧 runner 和 ADX 调度同时领取同一队列。回退只对未接受的新任务切换；在途任务先对账。所有历史卷、凭据和真实 PR 保留。

实施前仍需验证的设计假设

① 当前 VM 能否承载新增底座；② ADX 与 Compose 的实际连通和安全授权；③ 官方多根记录读取与终态刷新条件；④受限凭据与模型配置在选定后端的传递；⑤受管镜像的业务就绪。以上不阻止先评审架构，但不是已完成事项。
